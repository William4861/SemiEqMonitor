# 代码评审 checklist

> 单人项目里"评审"是自己给自己做。但**流程本身要真的走**：
> 开 PR 前逐条过一遍，不通过就不合并。这既是质量控制，也是面试时能讲清的工程习惯。

---

## 一、合并前必过（阻断项）

### 1. 能构建
- [ ] `scripts\build.bat` 通过，**零警告**（`-Wall -Wextra`）
- [ ] 新增/修改了协议或统计逻辑 → **补了单元测试**，且 `scripts\run.bat test` 全绿

### 2. 不破坏既有行为
- [ ] 改动了 Modbus 帧结构 / 数据库表结构 → **同步更新了 `docs/协议说明.md` 或 `docs/数据库设计.md`**，并升 `CHANGELOG.md`
- [ ] 版本号只在 `CMakeLists.txt` 改（不要在代码里硬编码版本字符串）

### 3. 线程安全（本项目最容易出事的地方）
- [ ] **没有在工作线程里碰任何 UI 对象**（`setText` / `update` / `QMessageBox` 等）
- [ ] 跨线程传自定义类型 → `Q_DECLARE_METATYPE` **和** `qRegisterMetaType` **都写了**
- [ ] 工作线程持有锁时，不会再调用同样加锁的函数（`QMutex` 非递归 → 会死锁）

### 4. 内存与资源
- [ ] 所有 `new` 出来的 Qt 对象：要么有 parent（对象树回收），要么有明确释放位置
- [ ] 新增的 socket / timer / thread 都有对应的停止与回收路径
- [ ] 没有在类里裸持 `new` 出来的非 Qt 资源而不写析构

### 5. 错误处理
- [ ] 失败路径有返回值或信号，**没有静默吞掉**
- [ ] 用户能感知的错误有提示；内部错误至少写日志
- [ ] 新加的日志带了模块名（用 `LOG_*` 宏，不要裸 `qDebug`）

---

## 二、代码质量（建议项）

### 6. 命名与结构
- [ ] 命名符合规范：类 `PascalCase`、成员 `m_`、常量 `k`、函数 `camelCase`
- [ ] 函数职责单一，超过约 60 行考虑拆分
- [ ] 嵌套层数 ≤ 3（用早返回代替深层 if）

### 7. 注释
- [ ] 注释解释**为什么**，不是复述代码
- [ ] 踩过的坑/有意的取舍写明了（例如"这里每条 flush 是有意的性能取舍"）
- [ ] 没有留下 `TODO` 而不写清"何时做"

### 8. 可测性
- [ ] 纯逻辑（解析、计算）抽成**静态函数或独立类**，不依赖网络/界面
- [ ] 新增的魔法数字已提取为具名常量

### 9. 性能
- [ ] 循环里没有重复的字符串拼接 / 容器拷贝
- [ ] 高频路径（采集回调）里没有不必要的内存分配
- [ ] 传给信号的容器用 `const &`，没有意外拷贝

### 10. UI 手感
- [ ] 界面刷新不引起闪烁（曲线与表格只更新变化部分）
- [ ] 长时间运行内存不增长（曲线/表格有上限，或定期清理）

---

## 三、提交前

- [ ] commit message 符合 Conventional Commits，且**说明了为什么**
- [ ] 一个提交只做一件事
- [ ] `DEVLOG.md` 记了今天的目标 / 完成 / 问题 / 解决
- [ ] 新发现的缺陷记入 `BUGS.md`
- [ ] `CHANGELOG.md` 的「未发布」段落已更新
- [ ] PR 描述写了：**变更说明 / 怎么验证 / 风险点 / 截图或日志**

---

## 四、提交信息格式

```
<type>(<scope>): <subject>

<body：为什么这么改，而不是做了什么>

Refs: #<issue 号>
```

`type` 取值：`feat` / `fix` / `docs` / `refactor` / `test` / `chore` / `perf`

**示例**

```
fix(acquisition): 修正 Modbus 响应帧字节序

温度读回来一直是天文数字，原因是我按小端解析了寄存器值。
Modbus 规定所有多字节字段为大端（网络字节序），改为 qFromBigEndian 语义。
同时补了 4 个数据驱动的单元测试锁住这个行为，防止回归。

Refs: #7
```

> 注意 `subject` 用中文也可以（团队内一致即可），但**要能一眼看出改了什么**。
> 反例：`fix: 修改bug` —— 等于没说。
