# 技术方案

> 本文说明**架构分层、模块职责、关键设计决策**。
> 重点记录"**为什么这么选**" —— 面试官更关心取舍理由，而不是功能列表。

---

## 1. 技术选型

| 选择 | 理由 | 备选与否决原因 |
|---|---|---|
| **C++11** | 目标岗位 JD 普遍要求 C++11/14；`enum class`、智能指针、lambda 足够用 | C++17 的 `std::optional`/`variant` 虽好，但本机工具链与部分岗位版本不一致，不冒进 |
| **Qt 5.14 Widgets** | 工业上位机事实标准；信号槽天然适配"采集线程 → UI 线程"的跨线程通信 | Qt Quick/QML 更适合消费级动效界面，工业 HMI 更常要求 Widgets |
| **CMake** | 跨平台、企业主流；多目标（库 + 两个程序 + 测试）管理清晰 | qmake 更简单但岗位提及率低 |
| **自绘 QPainter 图表** | 不引入额外模块；实时曲线只需"折线 + 坐标轴"，自绘更可控，且能在面试中讲透绘制原理 | Qt Charts 依赖额外模块、定制成本高；QCustomPlot 属第三方，需额外维护 |
| **SQLite** | 单文件零部署，设备端软件标配；`QSqlDatabase` 直接支持 | MySQL 需独立服务，对单机上位机是负担（MES 侧才需要） |
| **Modbus-TCP 为主** | 工业设备最通用协议；TCP 便于用模拟器复现，无需串口硬件 | 先用串口会把进度绑死在硬件上（串口通道排期在 D2 补） |
| **Ninja 构建** | 增量编译快，适合高频迭代 | Make 在多目标场景更慢 |

## 2. 分层与职责

```
表现层 UI ── 业务层 Service ── 采集层 Acquisition ── 设备
                    └── 持久层 Data
```

| 层 | 目录 | 职责 | 依赖方向 |
|---|---|---|---|
| **表现层** | `src/ui/` | 界面渲染、用户交互；**只做展示与转发，不含业务规则** | 依赖业务层信号，不直接碰 socket/数据库 |
| **业务层** | 排期中 | 数据解析、报警判定、SPC 统计、良率计算、报表与 MES 上报 | 依赖采集层接口与持久层接口 |
| **采集层** | `src/acquisition/` | 与设备通信、协议编解码、采集调度 | 只依赖 `common`，不知道界面与数据库存在 |
| **持久层** | `src/data/` | 建表、写入、查询、导出 | 只依赖 `common` |
| **公共** | `src/common/` | 领域模型、日志、版本 | 不依赖任何其他层 |

**依赖箭头只向下**：UI 不 include `QTcpSocket`，采集层不 include `QWidget`。
这样换协议只改采集层、换界面只改 UI 层。

## 3. 关键设计决策

### 3.1 为什么要 `IDeviceClient` 抽象层

**问题**：数据来源有三种可能（Modbus-TCP 真实设备、串口设备、模拟器）。若业务层直接 `new QTcpSocket`，
换一种来源就要改业务代码，且无法在单元测试中替换掉真实网络。

**方案**：定义纯虚接口 `IDeviceClient`，只暴露"连接 / 断开 / 轮询"三个动作和三类信号
（`connected` / `disconnected` / `parametersRead`）。实现类各自负责协议细节。

**收益**：
- 换协议不改上层（开闭原则）
- **单元测试可以注入 Fake 实现**，不依赖网络
- 三种来源可**运行时切换**（配置文件决定实例化哪个实现）

### 3.2 为什么设备模拟器要独立成程序

**问题**：真实半导体设备几十万，拿不到。但"粘包/拆包、断线重连、超限报警"这类问题
**只有对端真实存在时才会暴露**；用打桩（stub）返回值测不出协议问题。

**方案**：写一个独立的 `SemiEqSimulator`，用真实 Modbus-TCP 协议对外服务。

**收益**：
- 开发期不阻塞（不依赖硬件到货）
- **任何人都能一键复现完整演示** —— 对求职项目来说，可复现性本身就是可信度
- 可以**主动制造故障**（温度飙升、强制断线），验证上位机的容错

**关键取舍**：模拟器**不链接 `semieq_core`**。因为真实世界里"设备"与"上位机"分属不同厂商、不同代码库；
共用一个库会掩盖"协议才是唯一契约"这一事实。

### 3.3 版本的唯一来源

版本号只在 `CMakeLists.txt` 的 `project(VERSION)` 写一次，
通过 `configure_file()` 生成 `common/version.h`，代码、关于对话框、状态栏统一读取。

**收益**：改版本号只改一处，避免"界面显示 v1.0 但安装包叫 v0.9"这类经典不一致。

### 3.4 日志为什么自己写而不用 `qDebug`

| 需求 | `qDebug` | 本项目 `Logger` |
|---|---|---|
| 分级过滤 | 需编译期宏 | 运行时可调 |
| 带模块名 | 手动拼 | 宏统一注入 |
| 落盘 | 需 `qInstallMessageHandler` | 直接支持，目录不存在自动创建 |
| 崩溃不丢 | 缓冲区可能丢 | **每条 flush** |
| 线程安全 | 是 | 用 `QMutex` 保证 |

设备软件的日志是"事后诊断的唯一证据"，所以"每条 flush" 是有意为之的性能取舍。

### 3.5 跨线程传自定义类型的两个必要步骤

`Q_DECLARE_METATYPE(T)`（让类型"可注册"）+ `qRegisterMetaType<T>()`（真正注册）。
**只写前者不写后者**，QueuedConnection 会在运行时丢弃信号并打印告警 —— 这是采集线程 → UI 线程必踩的坑。

代码位置：声明在 `common/types.h`，注册在 `main.cpp`（程序启动时执行一次）。

### 3.6 Modbus 解析的防御性编程

TCP 是字节流，必须自己处理粘包/拆包。本项目在解析函数里逐项校验：

| 校验 | 拒绝条件 |
|---|---|
| 帧长 | < 9 字节 |
| 异常响应 | 功能码最高位为 1（**必须优先判断**，否则会把异常响应误报成"功能码不匹配"） |
| 功能码 | ≠ 0x03 |
| 字节数 | 为奇数 |
| 数据完整性 | 声明长度 > 实际可用数据 |

**这五条全部有对应单元测试**（`tests/test_modbus.cpp` 中 6 个异常输入用例）。

## 4. 线程模型（D4-D5 落地）

```
主线程（UI）
  └── MainWindow / 曲线 / 表格 / 报警列表
        ▲  QueuedConnection（信号槽自动跨线程排队）
        │
采集线程                         业务线程（可选）
  └── IDeviceClient               └── 解析 / 统计 / 入库
        │  poll() 周期触发
        └── QTcpSocket / QSerialPort
```

**铁律**：
1. **UI 只在主线程碰** —— 任何 `setText` / `update` 都不得在工作线程直接调用
2. 跨线程一律走信号槽；连接类型显式写 `Qt::QueuedConnection` 或用默认 AutoConnection
3. 生产者-消费者之间用**有界队列**，防止设备爆量时内存无限增长
4. 线程收尾：`quit()` → `wait()`，不要直接 `terminate()`

## 5. 错误处理约定

| 层级 | 处理方式 |
|---|---|
| 采集层 | 不弹窗、不退出；发 `connectionError(reason)` 信号 + 写日志；由上层决定重试 |
| 持久层 | 返回 `bool` + `lastError()`；调用方决定是忽略还是提示 |
| UI 层 | 用户可感知的错误用状态栏 / 消息框；其余只记日志 |
| 解析失败 | **丢弃整帧**而不是尝试部分恢复 —— 半帧数据比没数据更危险 |

**原则**：设备软件不能因为一次通信异常就崩溃或卡死，
但也绝不能**静默吞掉错误** —— 至少要有日志。

## 6. 编码规范

| 项 | 约定 |
|---|---|
| 命名 | 类 `PascalCase`；成员变量 `m_` 前缀；常量 `k` 前缀；函数 `camelCase` |
| 头文件 | `#ifndef` 卫哨；只 include 必要内容；能用前向声明就不 include |
| 注释 | 说明**为什么**，而不是复述代码；关键取舍与坑写明 |
| 编译 | 必须零警告（`-Wall -Wextra`） |
| 资源 | 优先栈对象 / 智能指针；Qt 对象有 parent 时交给对象树 |
| 魔法数字 | 不允许直接出现在业务代码里，提取为具名常量（如功能码 `kFuncReadHoldingRegs`） |

## 7. 风险与对策

| 风险 | 对策 |
|---|---|
| Modbus 协议细节耗时 | **先用最小可用实现打通链路**，再补异常分支；纯函数用单测锁行为 |
| 范围过大做不完 | 严守 P0 必达；三个里程碑检查点（D5 / D8 / D11）到点即砍 P1 后半段 |
| `QThread` 用法错误导致崩溃 | 只用 `moveToThread` + 信号槽；不在工作线程碰 UI；写单测兜底 |
| MinGW + 非 ASCII 路径 | 项目路径保持纯 ASCII（已踩坑，见 `BUGS.md` BUG-0001） |
| 长时间运行内存增长 | 曲线与表格只保留最近 N 点；数据库定期清理原始数据 |
